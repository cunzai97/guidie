# 鬼骰 · 大话骰 AI 对弈评测框架

> 两个模型同桌打大话骰。一条链路用来**观战**（浏览器竞技场），一条链路用来**量化**（无头评测）。
>
> 这个项目的重点不是"做个游戏"，而是**让模型博弈能力的评估变得可归因**：同一副牌、同一份规则、同一个提示词，结论能复现、能追责、能分组比较。

## 这是什么

大话骰的规则引擎 + 一套让 LLM 自由博弈的评测框架：

- **规则可配置**：内置两套规则，也能自己造一套（改斋的触发方式、破斋倍数、点数自由度、掉血倍率……），规则文本自动生成
- **同源双链路**：浏览器竞技场与无头评测共用同一份引擎、同一份解析器、同一份提示词，不存在"页面一套、评测另一套"
- **过程指标**：不只看胜负，还看开盅正确率、受骗率、诈唬率、判负率、平均重写次数——这些是分辨率更高的信号
- **指纹归因**：每次 run 都记 `prompt_hash` / `ruleset_hash` / `code_hash`，改了提示词或规则导致指纹变化时，前后两批数据**不能混进同一组对比**

```bash

# 可选：bash start.sh --open 自动打开浏览器；PORT=9000 bash start.sh 换端口

# 2) 配置模型
#    右上角「模型设置」→ 填 Base URL / 模型 ID / API Key → 保存
```

- **Node.js 18+**（用到内置 `fetch`）
- **Python 3.8+**（只用标准库）
- 没有任何 npm / pip 依赖
- 一个 **OpenAI 兼容端点**（llama-server、Ollama、vLLM、OpenRouter……都行）

浏览器端有三种方式，任选其一：

| 方式 | 做法 |
| --- | --- |

## 玩法

两人各 5 颗骰子，全场 10 颗。轮流喊价「n 个 m」，意思是"全场 10 颗里点数 m 至少有 n 个"。喊价必须严格大于上一手（加个数，或个数不变换更大的点数，点数序 `2<3<4<5<6<1`）。

轮到你时可以喊价，也可以**开盅**——质疑当前最高价那一手，全场亮牌结算：够数则喊价方赢，不够则开盅方赢。

- **1 是万能牌**（非斋状态时，双方手里的 1 都算数）
- **斋**：经典规则里喊到点数 1 就进斋，1 不再万能且锁死点数
- **劈**（新规）：和开盅一样亮牌结算，但双向结算——赢的 +1 血、输的 −1 血

**血量制**：双方开局各有 N 点血（上限也是 N）。每轮结算：输的一方 −1 点血；开盅时赢家不回血，劈时赢家 +1 点血（回满为止）。谁的血先降到 0 谁输掉整局——一场对局本来就会自然结束，而且越打越紧。

## 规则集

规则不是写死在代码里的一段文本，而是一份可切换、可自定义的配置。内置两套：

| id | 名称 | 语义 |
| --- | --- | --- |
| `classic` | 经典 · 喊 1 为斋 | 喊点数 1 即斋、锁死点数、1 不再万能；无转斋 / 破斋 / 劈。**逐字保留历史规则，指纹稳定，历史数据完全可比。** |
| `flex` | 鬼骰新规 | 取半向上取整转斋、点数全自由、2n+1 破斋、开盅只扣输家血、劈双向 ±1、首喊点数 1~6 且可直接喊斋。 |

`flex` 的完整语义：

- **转斋**：不抬价而改喊「斋」，个数 = `ceil(当前个数 / 2)`，点数 1~6 任意（**不限制必须喊 1**）；这一手起 1 不再万能
- **首喊点数 1~6**：喊 1 只是喊 1（未斋时也只数真 1），不会进斋——进斋只有「转斋 / 首喊写斋」两条路
- **首喊也可以直接喊斋**：开局第一手就能喊斋（没有上一手，不用取半）
- **喊点数 1 就是进斋**：不用另写「斋」，喊 1 之后本轮 1 不再万能（首喊喊 1 也直接以斋开局）
- **斋内抬价同普通规则**：唯一区别是 1 始终不算万能
- **破斋：个数 = 当前个数 × 2 + 1**，点数 2~6（喊 1 会立刻又进斋），必须写明「破斋」，破斋后 1 恢复万能。**一条规则就够**：因为转斋把 n 砍成 ceil(n/2)，而 2·ceil(n/2)+1 > n 恒成立，破斋后的最高价必然高于斋前——不需要再记「斋前那一手」，也不需要「整手必须超过斋前」这条附加条件（2026-11-09 是靠那条附加条件堵的循环，2026-11-10 改成 2n+1 后整条删掉）
- **劈**：与开盅完全一样（质疑同一手、同样亮牌），区别是双向结算：赢家 +1 血、输家 −1 血——开盅只扣输家血、赢家不回血，劈是唯一能把对手打得更狠（同时自己回血）的手段
- **结算**：双方开局各 N 点血（上限也是 N）。开盅：输家 −1 血（这一套里赢家不回）；劈：输家 −1 血、赢家 +1 血（回满为止）。谁的血先降到 0 谁输掉整局

**自定义规则**：设置抽屉「规则集」里可以「另存副本」，逐项改 16 个参数，右侧实时预览模型将看到的规则文本。自定义套存在 `settings.ruleSets`，CLI 用 `--rules <id>` 也能读。

### 单一真源

```
dice-rulesets.js   规则配置 + 生成给模型看的规则文本  ← 唯一来源
      │
      ├─→ dice-engine.js    legalActions() = 权威合法动作集合
      ├─→ dice-rules.js     checkLegal()  把错误翻译成人话
      └─→ context.js        buildSystem / buildUser / legalMenu / 结算行
```

任何一处硬编码规则描述都会造成"模型看到的规则"与"引擎实际判定"不一致——这个项目早期就踩过这类坑（见下方「一个真实的规则误读」）。

## 浏览器竞技场

全新前端：左右双选手卡直观对战、中央喊价台、流式实时推演、底部五个明细页（流水 / 决策明细 / 轮末复盘 / 统计 / 模型排名）。决策明细与轮末复盘也按甲方 / 乙方**左右分栏**。

- **内置机器人可直接上桌**：布阵下拉框的第二个分组是 `src/bots.js` 的 `BOTS` 注册表——`oracle`（纯数学地板）、`reader`（贝叶斯读牌）、`deep`（双向读牌 + 终盘）。机器人不连接口，`decideBot` 在页面里本地算一手（合法性与 LLM 走同一条 `checkLegal` + 落子路径，统计口径一致），所以能随时拿它当标尺：想量化「模型有没有超过算概率/读喊价的基线」，左右各配一局就行。机器人不产生 tok、不发复盘请求；对局照样进排名账本，席位记为 `base='bot'`、`model='<spec>'`，所以在榜单上就是一个可对照的天梯锚点（想只看真模型就按 `base` 过滤）。加新机器人 = 在 `BOTS` 里加一个 `{ label, desc, make }`
- **模型预设**：增删改 / 复制 / 测试连接 / 拉取模型列表 / 导入导出。配置写 `presets.json`（服务可用时）并同步 `localStorage`，服务没起也能用
- **每模型思考强度**：`off / low / medium / high / xhigh`。本地 llama-server 走 `chat_template_kwargs.thinking_budget`（1024 / 4096 / 12288 / 24576），远端走 `reasoning_effort`。两个字段都发，端点不认的会忽略。**默认是「中度」**（`settings.defaultEffort`），新建模型也继承中度；复盘请求固定 `off` 以省时。开战前还可直接在布阵区每个席位旁用「思考」下拉临时覆盖本局强度（跟随模型 / 关闭 / 轻度 / 中度 / 深度 / 极限），开战后锁定，不改模型存档
- **输出预算**：每个模型单独设，默认 8192
- **统计按模型左右对照**：底部「统计」页不是两个模型的数据合并，而是**每行一个指标、甲乙两列并排**。指标按「做这个动作的那一方」归属：决策手数 / 调用 / token / 耗时 / 截断 / 歧义 → 行动方；开盅次数 / 开盅正确 / 劈 → 开盅方；转斋 / 破斋 → 喊价方；判负 → 判负方。有明确优劣的指标（重写次数、耗时、截断、判负、开盅正确率、血量）会给胜出一方标金色。合并统计看不出"谁更快、谁更准"，所以拆开
- **亮色 / 暗色**：顶栏一键切，主题持久化
- **8k 预算与截断续写**：`finish=length` 且末行没有完整行动行时，保留未完思考、提示"接着原思路想完、立即决断"再给一次机会，不让"想深想就输"
- **并行复盘**：轮末复盘 `Promise.all` 同时问双方，等两份都回来再一起写回上下文——任何一方都不会读到对方这一轮的复盘
- **上下文生命周期**：① 局内全量（本局所有轮末复盘、所有逐手判断、所有亮牌事实）；② 轮末复盘继承同一份全量，写下的总结带到本局后续回合；③ 整局结束即全部清空，**不带任何东西到下一局**，每局从空白开始
- **判负口径**：三次无合法动作默认判负（与 harness 一致），可关「严格」回退到最小合法加价接手
- **落盘**：`calls.jsonl` 记 `run_id / seat / round / phase / model / ruleset_hash / effort / think_budget`，可与真值按主键对齐；整局结束另写一条 `matches.jsonl` 进排名账本（见下）

## 模型排名

底部「模型排名」页：历史对局浏览 + **按对手分计得失的 Elo 天梯**。每局结束（一方血量归零或轮数封顶）自动 POST 一条记录到 `/api/matches`，追加进 `runs/matches.jsonl`；中途重新布阵的半局不记。

**算法**（`web/ranking.js`，纯函数，浏览器与 `tests/test-ranking.js` 同源）：

```
E_A = 1 / (1 + 10^((R_B − R_A) / 400))
R_A += K × (S_A − E_A)        K = 32，初始 1500，胜 1 / 平 0.5 / 负 0
```

- **虐菜刷不动分**：赢低 200 分的对手只涨约 3 分，赢高 200 分的涨约 24 分；输给弱手重扣约 29 分。分数反映「赢了谁」，不是「赢了多少场」
- **按指纹分组**：每个 `(ruleset_hash × prompt_hash)` 组独立一张榜，跨指纹的胜负不混排（规则 / 提示词一改就是新榜）。`prompt_hash` 用纯 JS SHA-1 现算，与 `runlog.promptHash` 逐字节一致
- **身份 = 端点 + 模型 ID**：改别名 / 重建预设不分家；同模型自战不涨不跌
- **强度子榜**：选某档思考强度时只收「双方都用了该档」的对局，混档局只在「全部」里出现
- **定级中**：少于 5 场标 provisional；按时间顺序逐局更新，所以同胜负不同顺序分数不同（路径依赖是 Elo 的本性）
- 不按净胜分加权：初始血量 3 / 5 / 10 / 15 点的局不可比，只取胜负平

**账本一行**（`matches.jsonl`）：`t / run_id / gameNo / source / seats{A,B}(id,alias,model,base,effort,maxTokens) / ruleset_hash / prompt_hash / variant / rules / target / rounds / points / winner / draw / capped / stats{A,B}`。GET `/api/matches` 返回 `{"matches":[...]}`。无头 CLI 的历史 run 不进这张榜（旧指纹 + 复式换座 schema 不同）。

## 无头评测

浏览器适合看棋，量化模型能力用无头 runner。**判分全确定性、零 LLM judge。**

```bash
# 基线自检（零 token）：两个 bot 对打，验证链路
node src/pk.js --p0 reader --p1 oracle --deals 30 --out runs/bot-baseline.jsonl

# 模型 vs 基线（reader=读牌最强，oracle=纯数学地板）
node src/pk.js --p0 llm:8080:my-model --p1 reader --deals 6 --out runs/llm.jsonl

# 模型 PK
node src/pk.js --p0 llm:8080:model-a --p1 llm:8081:model-b --deals 10 --rules flex

# 分析
node src/analyze.js runs/llm.jsonl
```

**player 规格**：`deep`（最强基线）/ `reader`（贝叶斯读喊价）/ `oracle`（纯数学地板）/ `llm:<端口>:<模型名>` / `wb:<模型名>`（本地网关）。`threshold` / `random` / `always-open` / `never-open` 四个基础 bot 已于 2026-11-10 删除——它们的作用是「免费午餐检查」，但 reader 作为对手更严，留着只会分散注意力

**开关**：`--deals N --seed S --hp 血量 --max-rounds N --thinking on|off --effort off|low|medium|high|xhigh --rules classic|flex|<自定义id> --max-tokens N --temperature T --context chat|memory|snapshot --prompt <臂id>（当前只有 plain） --out 文件 [--append]`

`--hp N` 是**开局血量兼上限**（旧名 `--target` 仍可用）；血先归零的一方输掉整局。

### 三个设计要点

**复式赛**：每个 seed 打两局、第二局交换座位，同一副骰子对消骰运与先手优势（也暴露镜像协方差）。

**第一人称上下文**：给模型的每一行都是"你 / 对手"，明确身份、自己骰子 + 计数、比分、喊价归属、合法动作菜单。引擎的 `roundLine` 是上帝视角（甲/乙），**绝不喂模型**。

**归因**：解析 → 规则校验 → 最多重写 3 次；仍非法判负（forfeit），harness 不替模型走棋；连接彻底失败则该局"未评"。`finish_reason=length` 且末行无完整行动行时视为"想完但还没决断"：保留未完思考，提示「接着它想完、立即决断」再给一次机会（绝不说"请简短"，那会直接压掉推理）。

### 提示词臂

只有一套（`plain`，label「这局怎么赢」）：**完整规则 + 这局怎么赢（概率是入场券 / 进攻 / 防守）+ 一句收尾**。没有兵书、没有概率表、没有任何可执行结论。

- **概率是入场券**：双方都会算，算得准不构成优势。
- **进攻**：对手的每一手价都在暴露它——手里有多少该点数、哪个价位有货、从哪一手开始骗；加价幅度、转斋时机、开盅时机也是情报。
- **防守**：你的每一手同样在被反推。任何能总结成规律的习惯都是免费情报：有货才喊最贵，固定比例的诈唬也是规律，只在没货时开盅等于自报没货。防守要花钱，通常就是放弃这一手的最优。
- **一句收尾**：伪装自己，了解别人。对手也知道这一句。

规则段与这套说明一起压过一轮：flex 的 system 从 2662 字降到约 1000 字，规则段本身 682 字，一条只说一件事（不再有一条里塞三个例外）。语义没变，只有 `prompt_hash` 变。

**连败反思是拼接，不是替代**：`llm.js` 的 `reflect()` 写下的自省作为【连败后的自省】一段追加在「一句话」之后，规则与「这局怎么赢」原样保留。

**加第二套**：在 `src/context.js` 的 `ARMS` 注册表里加一个条目（`label / frame / guide / format / formatClassic / cue / summaryInstruction`）即可——`buildSystem`、`prompt_hash`、CLI `--prompt`、竞技场的提示词下拉都从这张表读。

### 纯数学 oracle 参照

`oracle` 是零训练、零拟合参数、确定性的**两层 expectimax**：精确二项/多项分布算概率，枚举对手 252 种手牌型；假设对手按「P<0.5 开盅、否则抬最真价」的数学打法，算到对手反抬后我方的最佳回应。它是「数学对数学」的**地板参照**——LLM 打赢它才算展现出超越算概率的博弈能力；但它不是 GTO 天花板，对手实际打法偏离模型假设时强度会打折。

校准（classic，100 deal 复式 = 200 局，target 10，seed 12345）：当年的对手是 `threshold(0.5)`，oracle 81.9% 胜（145 胜 32 负 23 平，配对 CI [0.74, 0.828]）、flex 78.6%；对 `random / always-open / never-open` 全胜；对 threshold 的过程指标是开盅正确率 0.369 vs 0.197、受骗率 0.023 vs 0.062。

**这四个基础 bot 已删除（2026-11-10）**，上面的数字只作历史留档、现在无法复现。留下来的两个对照是 oracle 与 reader：`reader` 对 `oracle` classic 98.3%（CI 95.8–100）、flex 60-0 零封（见下节）。

**首个 LLM 实测（2026-11-10，flex，`wb:minimax-m3.1-flash`，effort off / 2048 / chat / classic 臂，4 deal 复式 target 5）**：oracle **5-3** 胜（MiniMax 胜率 37.5%，配对 CI [0.125, 0.5]，小样本不能排除均势）。过程指标方向一致：开盅正确率 MiniMax 0.162 vs oracle 0.370，诈唬被抓 20 vs 6；零判负零截断零连接错误（输的是决策质量，不是规则理解）。MiniMax 的 3 胜全部来自**信息性喊价剥削**：oracle 的对手模型把喊价当无信息随机事件，「P<0.5 必劈」被真货价值喊价双倍收割（那 3 局 oracle 开盅 18 次只对 2 次）；但它自己的开盅纪律差，系列赛仍输。结论：纯数学地板能被「知己知彼」式打法剥削——这是设计内的能力信号；要把地板升成绝对标尺，需给对手模型加贝叶斯读牌（喊价即信息）乃至 CFR。

**首次血量制 + 大道至简实测（2026-11-10 17:xx，`runs/minimax-vs-reader-plain-flex-hp10.jsonl`）**：`wb:minimax-m3.1-flash` vs `reader`（贝叶斯读牌人机），flex，初始血量 10，2 deal 复式 = 4 局，`--prompt plain --effort medium --max-tokens 8192`。结果 **0-4**（配对 CI [0,0]，小样本）：MiniMax 开盅正确率 **0.436**、诈唬率 0.313、诈唬被抓 28；reader 开盅正确率 0.875。对比同日积分制 + classic 臂的同一对阵（0-4，开盅正确率 0.167），**大道至简臂把 MiniMax 的开盅判断准确率抬高了约 27 个百分点**，但面对会读喊价的对手仍然输——它输在「被读」而不在「算不准」：reader 的开盅正确率接近 0.9，而 MiniMax 每轮约三成诈唬且被抓 28 次。零判负零截断零连接错误，链路（解析/血量/格式）完全正常。

两个从这组数据里看到的设计问题：
1. **劈弱占优**：flex 里 `stake=1` 且开盅只有输家掉血，于是「劈对」比「开盅对」多赚 1 点回血、「劈错」与开盅代价相同——劈在不是满血时严格优于开盅。实测 4 局 90 次开盅里 61 次是劈，两边几乎无脑劈。要给回血加风险，把 `slashStake` 调到 2（经典套就是 ±2）即可恢复取舍。
2. **回血把对局拉长**：劈赢回血 + 双方频繁劈，导致血量在 10↔4 区间反复横跳，4 局里有 1 局直接打到 30 轮封顶（血量 3:8 判胜）。想保住「越打越紧」的紧张感，要么限制回血（如只回半血、或不封顶但让劈也扣自己），要么把初始血量降到 6~8。

### 最强基线 deep

`deep` 是 `reader` 的加强版，零训练、零拟合、确定性，只在合法动作集里选。相对 reader 的三处结构性修正：

1. **对手也会读我们**：reader 估「对手会不会开盅」时只用对手自己的手牌，等于假设对手不看我们的喊价。deep 维护两份后验——我方对对手手牌、以及对手对我方手牌——再让开盅概率按「对手自己的判断」算，诈唬的代价被算回来。
2. **叶子按手牌展开**：reader 的叶子先把后验塌缩成一个平均手牌，并把「抬价后继续博弈」记 0；deep 直接对「对手具体是哪手牌」逐条展开（我方手牌已知，真值是确定的），叶子给出开盅 / 反抬两条路的实际价值。
3. **效用换成败局概率**：reader 用固定 ±1 的相对分；deep 用「赢下整局」的概率差，终盘斩杀自动加权、自己只剩 1 血时自动保守。
4. 期望打平（差 < 0.001 赢局概率）时选让对手后验移动最少的那一手——同样赚，但少喂情报。

关键的一处工程决定：**对手类型要混合**。deep 单押「对手会读我」时，对 oracle 这种只看自己手牌的打法只赢 8.3%（模型错配）；把开盅概率按 `read=0.5` 混合「它读我」与「它只看自己」两种假设后，对 oracle 变成零封，对 reader 的优势不变。

实测（`--rules flex --hp 10`，复式＝每个 deal 双方各坐一次，血先归零判负、30 轮封顶按剩余血量）：

| 对局 | 样本 | 结果 |
| --- | --- | --- |
| deep vs reader · seed 12345 | 20 局 | deep 18-2（reader 胜率 0.10，95% CI [0, 0.25]） |
| deep vs reader · seed 777 | 30 局 | deep 26-3-1（reader 胜率 0.117，CI [0, 0.25]） |
| deep vs reader · seed 4242 | 40 局 | deep 35-5（reader 胜率 0.125，CI [0.05, 0.225]） |
| **合计** | **90 局** | **deep 79-10-1（88.8%）** |
| deep vs oracle · seed 99 / 31337 | 28 局 | deep 28-0（零封） |

复现：`node src/pk.js --p0 reader --p1 deep --deals 20 --seed 4242 --hp 10 --rules flex`。决策成本 55 ms/步（reader 135 ms）。

### 读牌 reader（贝叶斯对手模型）

`reader` 修掉 oracle 的可剥削点：不再把对手喊价当无信息随机事件，而是在 252 种对手手牌型上维护贝叶斯后验。生成模型——P(开盅|h)=logistic(γ·(0.5−P(当前价|h)))、P(喊 b|h)=(1−P开)·softmax(β·P(b|h))，再加 ε 均匀混合防模型失配；每看到一手喊价按似然更新权重，轮内累积、每轮重置（骰子每轮重摇）。开盅/劈 EV 用后验真值概率，抬价 EV 对后验做 expectimax，叶子用对手反价再更新一次后验。β/γ/ε 是固定行为假设，零训练、零对局拟合、确定性。期望枚举按「同面取最小个数」剪枝（策略等价类，|合法价| 54→12），信念更新仍用全支撑。

校准（target 10，30 deal 复式 = 60 局，零 token）：对 oracle **classic 98.3%（CI 95.8–100）/ flex 60-0 零封**（开盅正确率 0.477 vs 0.153）。当年对 threshold flex 也是 60-0（0.723 vs 0.152），那个 bot 已删除。同一局面下 v2（oracle）会劈的价值喊价，reader 不劈——唯一变量就是读牌。

MiniMax 实测（2026-11-10，flex、target 10、2 deal 复式 = 4 局）：**reader 4-0 完封**（10:-6 / 10:0 / 10:0 / 10:2，两座位各两局）。开盅正确率 **0.875**（16 开 14 对，其中劈 11 次）vs MiniMax **0.167**（36 开 6 对）；0 判负 0 截断 2 重写。对照：同一模型 target 5 对 v2 oracle 是 3-5 输——补上「读喊价」后一局都拿不下。成本 137 调用 / 33.6 credits。

本地模型实测（同参，`llm:1235:avalon-iq3ks-256k`，flex target 10，2 deal）：**reader 4-0**（10:0 / 10:1 / 10:4 / 10:-7），开盅正确率 **0.769** vs avalon **0.289**；155 调用 2 次 length 截断、12 次重写、**2 次判负**（第 4/5 轮的格式失败丢轮，非策略亏损，量化时需剥离）。avalon 的逐手推理里 78/123 次察觉到「套路被看穿」，但手牌级泄露（喊价即情报）只闪现 1 次（第 4 局喊自己没有的 4 污染对手信念），未固化成策略；chat 臂无轮末复盘，测的是临场能否想到。

**probBidTrue 修复（2026-11-10）**：引擎的二项尾概率此前从 c=1 起步而非 C(5,need)，整条概率被系统性低估（need=1 时 0.17 vs 真值 0.87）。只有 bot 在用这个函数；提示词里的概率表是独立写死的正确值，**prompt_hash 不变，历史 LLM 对局数据仍可比**；但所有基于它的 bot 旧数据作废。

### 落盘约定

- `--out` **默认覆盖写**（早期是追加，同一文件重跑会把两次实验混在一起；要续写显式加 `--append`）。落盘建议放 `runs/`（已 gitignore，页面代理的 `calls.jsonl` 与服务日志也在那里）
- 每次运行生成 `run_id`，首行 `kind=run-start` 写全量配置 + `prompt_hash` + `code_hash`，末行 `kind=summary` 标 `status=complete`；异常退出补 `run-aborted`
- 所有事件共用主键 `{run_id, deal, swap, game, round, step, seat, phase, ask}`，`call` 与 `game.events` 的真值可按主键直接对齐
- `analyze.js` 默认只统计 `complete` 的 run（`--all` 强制纳入中断实验）

### 过程指标

胜负之外的高分辨率信号（引擎持真值，零成本）：开牌正确率（ToM 直接度量）、受骗率、诈唬率 / 被抓、forfeit、平均重写次数。

还有一组**预算健康度**指标：`truncRate`（静默截断率）、`ambiguousRate`（解析多候选率）、`avgPromptTokens` / `avgCompletionTokens` / `cacheRate` / `avgCallMs`。

> 截断率高时胜负主要由输出预算决定，**不要据此比较模型能力**。

## 上下文复用口径

两条链路的"复用"不是一回事，比较结果前先对齐口径。

### 浏览器竞技场：内容级全量，局间清空

代理只透传 `messages`，不维护会话；每一手仍新建 `[system, user]` 两条消息（没有 assistant 历史），所以**不是对话级复用 / KV cache 复用**，前缀能稳定命中的只有 system 那一段。但**信息层面**已按局内全量打通：

| 阶段 | 模型能看到什么 | 边界 |
| --- | --- | --- |
| ① 局内（本局每一手） | 本局所有轮末复盘 + 所有逐手判断与落子 + 所有亮牌结算事实 + 当前局面 | 不做静默截断。超预算时只折叠**最早**几轮的逐手判断并明确标注 |
| ② 轮末复盘 | 继承同一份全量上下文，再加收束事实与复盘指令 | 跳过本轮结算行，避免重复 |
| ③ 下一局 | 空白开始 | 上一局的复盘与逐手分析全部清空，不做任何跨局继承 |

### 无头评测口径

- `--context chat`（默认）= **对话级真复用**：`messages` 持久、`buildTurn` 增量追加、system 只发一次、重试脚手架不入史
- `--context memory` = 摘要链：`summarize()` 用 `[system, ...backbone, ...working, summaryPrompt]`，跨局按 deal/game reset
- `--context snapshot` = 不复用（对比臂）

> ⚠️ 页面的复盘口径**不能外推到 CLI 默认模式**：CLI 默认 `chat` 模式全程不调用 `buildSummaryPrompt`，想对齐页面口径要显式 `--context memory`（摘要链同样只在局内，跨局 reset）。

## 归因指纹

**规则集或提示词一变，指纹必变。跨指纹的 run 不能混进同一组 A/B 统计。**

| 规则集 | `ruleset_hash` | `plain` 臂 `prompt_hash` |
| --- | --- | --- |
| `classic` | `413e1d1d` | `d333411b040b` |
| `flex` | `a6e4a59c` | `ed3b427ac0b5` |

`firstZhai` / `breakPlus` / `openLoserLoses` 只在 `half` 套里才有意义，不参与经典套哈希——所以给规则加参数不会让经典套的指纹漂移。`flex` 在 2026-11-09 连做两处语义修正：破斋必须严格大于斋前一手（堵压价死循环）、计分改为开盅只赢家 +1 / 劈才 ±1；`ruleset_hash` 由 `dc7a1605` → `4211d6fb` → `b680b754`：**修复前的 flex run 与修复后不可比**。2026-11-10 移除跨局整局复盘继承（只保留轮末复盘带到下一轮），轮末复盘指令的生命周期描述随之改为「整局结束即清空」，并删掉整局复盘指令文本：**四个臂的 `prompt_hash` 全部变化**（classic 臂 `01707c0ad70a` → `04acb400bcba`、probe 臂 `9d0396ea3639` → `e8338cfb73f1`；flex 对应 `be8b49467564` → `17207d104e1b`、`5956cfdba120` → `f10b6e2cdfb3`），此前的 run 与此后不可比。

**2026-11-10 计分从「积分制」彻底改成「血量制」**（输家掉血、归零判负、劈双向回血封顶上限）：结算口径变了，两套规则集的 `ruleset_hash` 一起并入 `|hp=1`（`classic` `177d9fc1` → `413e1d1d`），模型可见的结算文案与血量行也随之改写。**积分制时代的全部历史 run 与血量制不可比**，包括上面那段 oracle 实测。

**同日还有两次规则语义收紧**：破斋改为「个数至少翻倍（不是正好）+ 整手严格超过斋前那一手 + 必须写明「破斋」二字」，以及「任何喊价的个数不得少于 2 个（转斋取半后不足 2 个就不许转）」。`flex` 的 `ruleset_hash` 随语义版本并入 `|bv=2`、`|mn=2`、`|sv=2`、`|nr=1`，加上首喊点数放开到 1：`bbf8a642` → `6c051395` → `f0bf979b` → `405e1733` → `a9bf39ff` → `663ae23e`，**此前的 flex run 一律与之后不可比**。

**同日修掉一个合法动作集合的 bug**：`flex` 下「个数不变、把点数换成 1」被引擎判成非法（`|sv=2`），但 1 是点数顺序里最大的、规则正文也写明 `2<3<4<5<6<1`，报错文案还会自相矛盾地提示「点数要换成比 X 更大的」。现在未斋与斋内都放行（未斋换到 1 只数真实 1，也不会进斋）。

**破斋门槛改成「两倍 + 1」（`|bv=3|bp=1`）**：旧版是「至少翻倍 + 整手严格大于斋前那一手」两条，实现在轮内维护 `preZhai` 记账，规则文本也要写两条条件加一个例子。改成 2n+1 之后一条规则就够——`2·ceil(n/2)+1 > n` 恒成立，破斋天然高于斋前，`preZhai` 与 `breakMustExceed` 整块删除，引擎、规则文本、合法菜单、bot 的假设局面镜像同步简化。指纹 `663ae23e` → `c3f2fd4f`。

**同日再加一条合法性约束：同一手不能重复喊**（`|nr=1`）。转斋把个数砍半，价格于是能绕回本轮早就喊过的位置——实测出现「3个6 → 2个6斋 → 2个1 → 4个6破斋 → 2个1转斋」，第 5 手和第 3 手完全一样，等于同一个承诺喊了两遍还把最高价整体拉低。现在本轮出现过的「X 个 Y」不再进合法集（不管写不写斋/破斋），模型会收到「本轮已经喊过『2 个 1』，同一手不能重复喊」的重写提示。代价是极端局面下可能出现无价可喊（只能开盅）：随机乱喊压测里约 1.5%，bot 对局里 0%。

**提示词臂也在这天收敛为一套**：删掉 `classic`（兵书）与 `probe`（轻量引导）两个臂，只保留「这局怎么赢」这一套；`ARMS` 注册表把接口留好，加新臂不影响其它代码。

## 一个真实的规则误读

这个项目的规则文本被反复打磨过，起点是一次实测。

某局第 5 轮，甲方模型手里 2 张 3、没有 1，对手喊「7 个 3」。正确解是**直接开盅**（全场 3 最多 7 个，需要对手 5 颗全是 3 或 1，概率约 0.41%）。

模型却写：「升到 8 个 3 后全场必然不足，就应把对手逼入只能开盅认输的位置」，然后喊了 8 个 3，对手当场开盅拿分。

复盘发现：它把「开盅质疑的是**开盅前最近的一手**」错记成「永远质疑对手之前喊的 7 个 3」，还误以为「我方没有 1 就不存在万能牌补足」（**对手的 1 同样算**）。

引擎逻辑、规则条款、上下文供给全部核对无误——**是规则应用算反，不是规则没给**。于是规则文本做了立场中立的改写：明确「只要你抬出一手新价，最新一手就换成你喊的」「双方手里的 1 都算万能牌」。

代价是两臂 `prompt_hash` 同时变化，所以规则澄清前后的 run 必须分组统计。**这是纯规则归属澄清，不含任何"该开还是该喊"的策略结论。**

## 已知边界

- **无头评测默认 `chat` 上下文全程不调用轮末复盘**——想用复盘要显式 `--context memory`
- **页面只采集 `completion_tokens`**，没有 `prompt_tokens` / `cached_tokens`，KV cache 是否命中在页面侧不可测（CLI 侧有 `cacheRate`）
- **`--out` 默认覆盖写**，同一文件重跑会覆盖旧数据（这是刻意的，见「落盘约定」）
- **"可复现"目前只保证骰子**：模型侧 seed 未固定，`temperature` 默认 0.7
- 基线 bot 是**校准参照**而非不可战胜的标准；oracle 也只是「数学对数学」地板，不是 GTO 天花板——打赢 oracle 是博弈能力的必要非充分证据
- **2026-11-10 前的 threshold 基线数据作废**（probBidTrue 二项系数 bug，见「纯数学 oracle 参照」）；LLM 历史数据不受影响

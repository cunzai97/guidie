# LLM 裁判（LLM Referee）设计规划

> **状态：仅规划，未实现。** 本文只定义契约、边界与实施路线，仓库中没有任何一行 LLM 裁判的代码。
> 文中引用的函数名、文件均为当前仓库的真实实现，规划以它们为锚点。
>
> 目标读者：想改造这个项目，或想在自己的评测里加入「模型当裁判」的开发者。

---

## 1. 为什么要做这件事

现在的裁判是**代码裁判**：`dice-rules.js` 的 `checkLegal(round, action)` 拿引擎算出的权威合法动作集合 `dice-engine.js` 的 `legalActions(round)` 做判定，返回 `null` 表示合法、否则返回一句人话理由。

它的优点和代价都很明确：

| | 代码裁判 | 代价 |
| --- | --- | --- |
| 判定依据 | `legalActions()` 枚举出的闭集 | 规则没被枚举到 = 一定判非法，裁判无法"变通" |
| 规则表达能力 | 只能表达 `dice-rulesets.js` 里那 16 个字段能描述的规则 | 想玩新规则就得改代码、重新出指纹 |
| 一致性 | 逐字确定，同一副牌同一动作永远同一结论 | 无法考察"模型自己理解规则"这件事 |
| 可解释性 | 理由是模板拼的 | 同上 |

**LLM 裁判要解决的是第二条**：让规则不再由代码枚举死。裁判拿着规则文本（由 `dice-rulesets.js` 生成给模型看的那一份）自由解释，一手「喊 8 个 3」在经典套下代码必然判非法，但换一套允许"跳叫"的自定义规则，裁判就可能判它合法并解释为什么。规则因此从"代码里的枚举"变成"裁判的裁量"。

它同时带来一个**必须正面处理的新问题**：裁判也是模型，也可能错。所以这份规划的重点不在"怎么让裁判判对"，而在**把裁判的裁量权关进一个可控的笼子里**。

## 2. 核心设计张力（先讲清楚约束，再讲方案）

### 2.1 单一真源 vs 自由裁量

项目当前最重要的架构承诺是「规则单一真源」：引擎合法性、行动解析、给模型看的规则文本三者同源，源自 `dice-rulesets.js`。LLM 裁判天然与这条承诺冲突——它就是来打破"引擎说了算"的。

**结论：不打破，而是分权。** 把"裁判"拆成三层，越权的事物理上做不了：

```
L0  物理不变量   代码，硬边界，不可突破
    ────────────────────────────────────────
L1  规则裁量     LLM 裁判，在 L0 之上解释规则、判定合法性
    ────────────────────────────────────────
L2  事实结算     代码，引擎算点数、算血量、判胜负
```

- **L0 由 `dice-engine.js` 负责**：`count` 必须 ∈ [1, 10]（全场就 10 颗骰子）、`face` 必须 ∈ [1, 6]、一轮里必须有人喊过价才能开盅、血量结算符合当前规则集（开盅/劈各自的 stake 与赢家是否回血）。裁判可以判「这一手合法」，但**不能凭空造出 12 个 6**。
- **L1 由 LLM 裁判负责**：这手价格合不合规则、斋状态该不该切、这一手算不算破斋、点数能不能换——凡是需要"读懂规则文本"才能回答的，归它。
- **L2 仍由代码负责**：喊价成立与否、实际有几个点、谁赢谁输、血量加减多少。**裁判永远不能决定骰子点数和结算结果。**

这条分界是整个设计的支点。一旦允许裁判碰 L2，裁判就能"改点数"，评测直接变成自己骗自己。

### 2.2 裁判不能看到手牌

代码裁判不看手牌（`checkLegal` 只吃 `round` 的公开状态）。LLM 裁判必须严格同规格：**输入里只有公开信息**——轮次、比分、喊价序列（含每一手的状态标签）、当前规则文本、历史裁定。

裁判**不能**看到：任何一方的 5 颗骰子。如果裁判看得到牌，它就能基于"其实我方有 3 张 6"来判"喊 8 个 6 合理"，那是替选手作弊。

> 实现约束：裁判请求的构造必须走一个**独立的构造函数**，不能复用 `context.js` 的 `buildUser`（那个是给选手看的、含自己手牌）。见 §5 的 `buildJudgeInput()`。

### 2.3 裁判会被"说服"

LLM 裁判读到的输入里包含选手的**原文输出**。一个足够强的选手，写一段"根据本桌规矩，应当允许 X"的说理，裁判很可能被带偏。

**防护（分三层）**：

1. **单向**：裁判只看不说，输出只有一份裁决 JSON，不与选手对话。选手拿不到裁判的理由文本，只拿到「不合法 + 一句话理由」。
2. **无利益**：建议强制「裁判实例 ≠ 参赛模型实例」。同一个模型既打牌又当裁判，等于自己给自己打分。UI 上至少要给醒目警告。
3. **裁定账本**：每一手已经生效的裁定都累积进「裁定账本」并回灌给裁判，让它在同一局内**自我一致**。裁判不能第 3 轮说「这合法」第 7 轮又说「同样的话不合法」。

裁定账本还有一个副作用好处：它让整套裁定可审计、可复盘——每一步为什么判成这样，事后能查。

### 2.4 裁判自己也会幻觉

裁判可能返回：非 JSON、缺字段、count 不合法、说"这一手合法"但没给动作。

**防护**：裁判输出必须走**结构化协议 + 二次校验**。裁判说合法但动作不合法 → 这次裁决作废，按非法处理（并且这次本身要记成指标）。绝不因为"裁判说合法"就放行一个越界的动作。

### 2.5 评测口径会被破坏

代码裁判下，胜负只由**骰子 + 选手决策**决定，可复现（种子化 RNG + 同一副牌两局交换座位）。引入 LLM 裁判后，同一副牌可能因为裁判的临场解释不同而产生不同结果。

**这不是缺陷，是 LLM 裁判的固有代价，必须在评测报告里显式声明。** 对策：

- 归因指纹新增 `judge_hash`（裁判提示词指纹）/`judge_model` / `judge_mode`。
- 开启 LLM 裁判的 run **单独分组统计**，绝不与代码裁判的 run 混进同一组 A/B 对比。
- 报告里必须同时给出「裁判翻转率」：裁判判合法的动作里，代码裁判判非法（或反之）的比例。这个数字是裁判质量的直接度量，比胜负更有信息量。

## 3. 架构：裁判作为第四个组件

```
                    ┌──────────────┐
   甲模型 ──输出──▶ │              │
                    │   规则引擎    │ ◀── 规则集 dice-rulesets.js
   乙模型 ──输出──▶ │  (L0/L2)     │      （同时生成给裁判看的规则文本）
                    │              │
                    └──────┬───────┘
                           │ 候选动作 + 公开状态
                           ▼
                    ┌──────────────┐
                    │   LLM 裁判   │  ◀── 裁判模型（设置里独立配置）
                    │  (L1 裁量)   │      输入：公开状态 + 规则文本 + 裁定账本
                    └──────┬───────┘
                           │ 裁定 JSON
                           ▼
                    ┌──────────────┐
                    │  裁决执行器  │  校验 schema → 落进 L0 → 推进状态
                    └──────┬───────┘
                           ▼
                    引擎推进 → 下一手 / 结算
```

关键点：**裁决执行器是新的仲裁层**，它不信任裁判也不信任选手，而是把两者都当作输入源，自己做最终确认。

### 3.1 三种裁判模式

设计成一个三档开关 `judge.mode`：

| mode | 裁判是谁 | 合法性判定 | 用途 |
| --- | --- | --- | --- |
| `code` | 代码 | `checkLegal()` | 默认，历史 run 可比 |
| `llm` | 设置里配置的 LLM | LLM 裁判（受 L0 约束） | 考察"规则自由度"、跑新规则 |
| `shadow` | 两者都跑 | 代码为准，LLM 只记录不改判 | **调研用**：测裁判准不准，不影响对局 |

`shadow` 模式是**最有价值的默认推荐**：它不改变任何现有结论，却能持续产出"代码裁判 vs LLM 裁判"的分歧数据集——先验证裁判质量，再决定要不要开 `llm`。

## 4. 规则契约：给裁判看什么

裁判看的规则文本**直接用 `dice-rulesets.js` 的 `rulesText(rules)`**，与选手看的同一份（同源原则不变）。区别只在**评委视角的补充说明**：

```
规则文本（与选手同一份）
+ 本桌当前生效的规则集 id 与 ruleset_hash
+ 本局已生效的裁定账本（逐条：第几手 / 选手写了什么 / 裁定结果 / 一句话依据）
```

**不加**的东西（重要）：
- 不给裁判任何"选手可能的意图"分析；
- 不给概率表、胜率估计——那会让裁判带策略偏见去判合法性；
- 不给裁判自己上一轮的裁决理由以外的任何评判材料（避免锚定到某一种解释）。

### 4.1 裁定账本（ruling ledger）的格式

```jsonc
{
  "round": 3,
  "step": 7,
  "seat": "A",
  "claimed": "喊 8 个 3",          // 选手原文里解析出的动作（若有）
  "raw_excerpt": "……全场最多 7 个 3，所以应该开盅……",  // 截断到 200 字
  "ruling": "illegal",             // legal | illegal | unsupported
  "normalized": null,              // 合法时：引擎可执行的动作对象
  "reason": "本桌规矩是新价必须严格大于上一手；上一手是 7 个 3，8 个 3 更大，但点数不可在个数不变时下调……"
}
```

账本每轮增长，随 `ctxBudget` 截断（保留最近 N 条 + 最早的条数统计），避免裁判上下文无限膨胀。截断策略必须在裁判提示词里说明，否则裁判会以为自己漏看了历史裁定。

## 5. 裁判协议

### 5.1 输入

裁判请求**独立构造**，不复用 `context.js` 的 `buildUser`（含选手手牌）。

```
system: 裁判 system prompt（新增，独立指纹）
        - 角色：规则裁定者，不是对手
        - 职责：只回答"这一手是否被本桌规则允许"
        - 明确的禁止项：不要给策略建议、不要评价对手、不要建议最优解
        - 输出格式：严格 JSON
user:   公开局面 + 规则文本 + 裁定账本 + 待裁定的动作
```

**关键：`user` 里必须显式声明"你看不到任何人的手牌"，并把"这一点本身就是裁定依据"写清楚**——例如"喊 5 个 6 是否成立取决于牌，但本裁定只问『规则允不允许喊这一手』"。否则裁判会因为"不知道牌面"而拒答或要求看牌。

### 5.2 输出（结构化）

裁判必须返回严格 JSON：

```jsonc
{
  "legal": true | false,
  "action": {                      // legal=true 时必填：规范化后的引擎可执行动作
    "type": "bid" | "open",
    "count": 5,                    // type=bid
    "face": 6,                     // type=bid
    "mode": "normal" | "toZhai" | "breakZhai",   // 缺省 normal
    "slash": false                 // type=open 时可为 true（劈）
  },
  "reason": "一句话，不超过 60 字",
  "rule_basis": "引用了哪条规则（自由文本）"
}
```

`action` 的字段**与 `dice-engine.js` 的动作模型一一对应**（`bid{mode}` 与 `open{slash}`），裁判因此不需要发明新的动作语法。

### 5.3 输出校验（裁决执行器）

裁判返回后，执行器按顺序做四道检查，任何一道不过就作废本次裁决：

1. **schema 检查**：是合法 JSON；`legal` 是布尔；`action` 字段类型正确。
2. **L0 不变量检查**：`count ∈ [1,10]`、`face ∈ [1,6]`、`mode` 是三选一、`slash` 是布尔。
3. **交叉检查**：`legal=false` 时不应带 `action`；`legal=true` 时 `action` 必须能通过 `E.normalizeAction()`。
4. **状态机检查**：`action` 必须能落进当前 `round` 的合法上下文（例：首喊不能带 `mode:'toZhai'` 而规则集没开 `firstZhai`；开盅必须已有喊价）。

**裁决作废时的处理**：按非法处理 + 记 `judge_invalid` 指标 + 走重试（给裁判一次带错误说明的重问机会，最多重试 2 次），仍失败则**降级到代码裁判**（`checkLegal`），并记 `judge_fallback`。

> 这里有个刻意保留的语义差异：LLM 裁判判**非法**是有效裁决（可以直接拒掉选手的动作，让选手重写）；只有裁判**自身输出不可用**才降级。降级方向是"更保守"，不会放宽 L0。

### 5.4 与选手的重写循环的关系

现在选手的循环是（`arena.js` 的 `decide()`）：解析 → `checkLegal` → 不合法就把理由回灌让选手重写（最多 3 次）→ 仍不合法判负（forfeit）。

接入 LLM 裁判后，这条循环**结构不变，只是换掉判定器**：

```
选手输出 → parseAction → [LLM 裁判 裁定] ─合法→ 引擎推进
                          │
                        └─非法→ 把 reason 回灌给选手重写（原有逻辑）
```

**裁决理由要改写成选手能懂的话**。裁判返回的是规则术语，选手的提示词是另一套语言，这里需要一个 `reasonForPlayer(ruling)` 适配（把 `rule_basis` 压成一句给对手看的话，不泄露裁判的完整推理链）。

## 6. 接口草案（仅设计，不实现）

以下签名是规划给实现者的接口约定。**当前仓库无对应实现。**

### 6.1 新模块 `judge.js`

```js
// UMD，与 dice-engine.js / context.js 同风格，供浏览器与 Node 共用

// 构造裁判输入（严格不含任何手牌）
function buildJudgeInput(round, rules, ledger, action) -> { system, user }

// 解析 + 校验裁判输出，返回裁决结果
function parseRuling(raw, rules) -> {
  ok: boolean,          // schema/L0 是否通过
  legal: boolean,       // 裁判的裁定
  action: object|null,  // 规范化动作
  reason: string,       // 给玩家的一句话
  basis: string,        // 裁判引用的规则
  error: string|null,   // 作废原因
}

// L0 硬边界校验（独立于裁判，裁判越权也拦得住）
function checkInvariants(round, action, rules) -> string|null

// 账本管理
function pushRuling(ledger, entry) -> ledger
function trimLedger(ledger, budget) -> ledger

// 对外主入口
function judgeAction(round, rules, ledger, action, opts) -> {
  ruling, ledger, fallback: boolean, elapsedMs
}
```

### 6.2 现有模块的改动点（规划）

| 文件 | 改动 |
| --- | --- |
| `dice-rules.js` | `checkLegal` 保留不动（`code` 模式与降级路径都用它）。新增 `checkLegal` 与 LLM 裁判的**分歧记录**钩子。 |
| `dice-engine.js` | `applyBid` / `resolveOpen` 增加 `lenient` 旁路：在 LLM 裁判模式下，跳过 `legalActionSet` 闭集校验，但**保留 L0 不变量校验**。这是让"裁判判合法的非常规动作"能真正落地的关键改动。 |
| `context.js` | 新增 `buildJudgeSystem()` / `buildJudgeUser()`（独立指纹，不进 `PROMPT_TEXTS` 选手臂）。`promptTexts()` 不变——选手的 prompt 指纹不能被裁判污染。 |
| `arena.js` | 设置里加「裁判」区：模式（code/llm/shadow）、裁判模型选择（从已有预设里选）、裁判思考强度。`decide()` 里把 `R.checkLegal` 换成 `judgeAction`。 |
| `runner.js` | 无头评测侧同样接 `judgeAction`；新增 `judge_mode` / `judge_hash` / `judge_flip_rate` 指标。 |
| `runlog.js` | `promptHash` 旁边新增 `judgeHash()`；run 清单写 `judge_mode` / `judge_model` / `judge_hash`。 |
| `dice-rulesets.js` | 规则集不变。裁判读的是同一份 `rulesText()`。 |

### 6.3 新增指标

| 指标 | 定义 | 意义 |
| --- | --- | --- |
| `judgeFlipRate` | LLM 裁判与代码裁判裁定不一致的次数 / 总次数 | 裁判有多"野"，以及新规则到底被用起来了多少 |
| `judgeInvalid` | 裁判输出未过 schema/L0 的次数 | 裁判的可靠性 |
| `judgeFallback` | 降级到代码裁判的次数 | 裁判可用性 |
| `judgeReasonTokens` | 裁判输出的理由长度分布 | 裁判是否在敷衍 |
| `lawFlips` | 同一局面同类表述被裁定不一致的次数 | 裁判的自我一致性（裁定账本是否起作用） |

`judgeFlipRate` 是这批指标里最有价值的：它直接量化了"代码裁判 vs LLM 裁判"的语义差距，也就是这套项目想研究的东西本身。

## 7. 失败模式与对策

| 失败模式 | 表现 | 对策 |
| --- | --- | --- |
| 裁判被说服 | 选手写一段说理，裁判就放行 | 单向 + 裁判≠选手 + 裁定账本锚定 |
| 裁判看不到牌就拒答 | 裁判答"无法判定牌面" | system 明确"只判规则合法性"；`unsupported` 独立枚举，不与 illegal 混 |
| 裁判自我矛盾 | 第 3 轮判合法、第 7 轮同样话判非法 | 裁定账本 + `lawFlips` 指标持续监控 |
| 裁判编造规则 | 引用不存在的条款 | `rule_basis` 必须引用规则文本里的原句；执行器可做关键词覆盖度检查（启发式） |
| 裁判输出格式崩 | 非 JSON / 缺字段 | schema 校验 → 2 次重问 → 降级代码裁判 |
| 裁判越权改事实 | 声称"实际有 7 个 3" | L2 完全不给裁判；输出里若出现点数声明直接丢弃并记 `judge_invalid` |
| 裁判拖慢评测 | 每手多一次 LLM 调用 | 裁判用小模型 + `effort:off`；`shadow` 模式异步旁路，不阻塞主循环 |
| 成本失控 | LLM 裁判 × 2 选手 × 30 手 × 10 deal | 裁判调用不计入选手 token 预算，但单独计费与单独记账 |

## 8. 实施路线（建议顺序）

**Phase 0 · 影子测量（不动对局）**
`shadow` 模式跑通，代码裁判照常判定，LLM 裁判只记录。产出分歧数据集，回答三个问题：LLM 裁判的 schema 合法率是多少？分歧集中在哪类动作？裁判的自我一致率如何？

> 这一阶段不产出任何对局结论，纯粹是裁判质量的体检。**在它跑出数据之前不要开 `llm` 模式。**

**Phase 1 · 接入裁决链**
`judge.js` 落地，替换 `decide()` 里的判定调用，`llm` 模式可用，但默认仍是 `code`。

**Phase 2 · 引擎宽松执行**
`dice-engine.js` 的 `lenient` 旁路，让裁判判合法的非常规动作能真正落进状态机。这一步风险最高，必须有 `test-rules.js` 的对拍用例兜底。

**Phase 3 · 归因与报告**
`judge_hash` / `judge_mode` 进 run 清单，`analyze.js` 出「裁判分歧」小节。

**Phase 4 · 规则集协同**
让 `dice-rulesets.js` 能描述"这段规则交由裁判裁量"（比如某条规则标为 `judge_discretion: true`，代码不强枚举，交给裁判判）。这一步才真正兑现"LLM 裁判能随意改规则"的初衷。

## 9. 开放问题（需要拍板）

1. **`llm` 模式下，裁判判合法的动作如果违反 `dice-rulesets.js` 的某个字段（比如 `maxCount`），听谁的？**
   规划倾向：听代码（L0 硬边界），字段级规则听裁判。但 `maxCount=10` 这类是物理约束，不该被裁判改。

2. **裁判能不能改"谁先喊"这类回合制状态？**
   倾向：不能。回合流转是引擎的事，裁判只判单手动作。

3. **`shadow` 模式下裁判与选手的提示词要不要共用 `context.js`？**
   倾向：不共用。裁判提示词独立成文件、独立指纹，共用会把"角色"串味。

4. **裁判是否也吃模型的 thinking？**
   倾向：默认 `off`。裁判要的是快速稳定的结构化输出，不是长推理。

5. **裁判用同一个模型实例会不会更好（自洽）？**
   倾向：不好，且应强制不同实例。理由见 §2.3。

## 10. 与现有架构的关系一览

| 现有承诺 | LLM 裁判引入后的状态 |
| --- | --- |
| 规则单一真源 | **保留但分权**。规则文本仍同源；判定权分给 L1，物理事实与结算仍归 L2。 |
| 确定性可复现 | **在 `llm` 模式下失效**，必须分组统计。`shadow` 与 `code` 模式下不受影响。 |
| 引擎持真值、零 LLM judge（README 原话） | **修订为**：默认零 LLM judge，`llm` 模式下裁判只判规则、不判事实。 |
| 归因可追 | **扩展**：`ruleset_hash` → 加 `judge_hash` / `judge_mode` / `judge_model`。 |
| 提示词两臂隔离 | **保留**。裁判提示词独立指纹，不进 `PROMPT_TEXTS`。 |
